# Building a RAG pipeline

Before documents can be searched, they are split into chunks, and each chunk gets its own embedding. Chunk size is a trade-off. Large chunks keep more context together, but their embedding blends several ideas into one vector, so a specific question matches them less precisely. Small chunks match precisely but can cut an explanation in half, leaving the retrieved text without the sentence that makes it useful. A common starting point is chunks of a few hundred words with an overlap of 10 to 20 percent, so a sentence near a boundary appears in both neighbouring chunks. Splitting at natural boundaries such as headings and paragraphs usually works better than cutting after a fixed number of characters.

In retrieval-augmented generation, the request is embedded with the same model as the documents, and the system looks up the chunks whose embeddings are most similar to it. It keeps the top k results, often between 3 and 10. Some systems also apply a similarity threshold and drop chunks below it, so an off-topic request retrieves nothing instead of the least bad matches. The retrieved chunks are added to the prompt, and the language model is told to answer from them. Retrieval quality limits answer quality. If the right chunk is not retrieved, the model either refuses or falls back on what it learned in training, which may be outdated or wrong. Retrieval also costs time, because every retrieved chunk makes the prompt longer, and a longer prompt takes longer to process, especially on a CPU.
